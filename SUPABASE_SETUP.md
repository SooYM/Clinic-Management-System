# Supabase database setup

The schema is defined by ordered migrations `supabase/migrations/20261005010000_clinic_foundation.sql`, `supabase/migrations/20261005020000_queue_transitions.sql`, and `supabase/migrations/20261005030000_clinical_document_lifecycle.sql`. They define Malaysia defaults (MYR and `Asia/Kuala_Lumpur`), clinic/branch-scoped staff membership, operational records, safe-default-deny RLS policies, immutable history tables, status-only document verification, atomic queue transitions, and versioned clinical document issue/revision/print RPCs.

## Apply the migration and provision access

1. Create a Supabase project in a region selected by the clinic/operator, then install/configure the Supabase CLI and authenticate it.
2. Copy `.env.example` to `.env.local` for local application configuration. The example contains placeholders only. Fill them locally; never commit them. Service-role and database URL values are server-only and must not be exposed to browser code.
3. Link this repository to the Supabase project using the Supabase CLI, then run `supabase db push` to apply the migration. For a disposable local project, use the normal Supabase local start/reset workflow.
4. Create clinic and branch records, then Supabase Auth accounts and a corresponding `public.staff_members` membership row for each user's clinic and branch. Provision the initial manager through a trusted administrative path; public self-enrollment is not enabled.
5. Explicitly insert each branch/role's allowed rows into `public.role_permissions`. Migrations seed no permissions: missing rows deny application access by default. Use the exact permission keys and table mapping in [database design](docs/database.md#rls-and-grants), including `queue.read`/`queue.manage` for queue reads/RPCs and `patients.identifiers.read` separately from `patients.read`. Review the clinic's role matrix before granting access. The manager role can manage permissions only after an initial manager membership is provisioned.
6. Configure the app to use the caller's authenticated session so PostgreSQL RLS applies. Use the service-role key only in trusted provisioning or background workers, and independently validate the caller/branch for privileged operations because service role bypasses RLS.

## Patient NRIC protection

Patient registration and identifier retrieval require two independently generated 32-byte server-only keys: `PATIENT_NRIC_ENCRYPTION_KEY` and `PATIENT_NRIC_HASH_KEY`. `.env.example` shows how to generate separate values with `openssl rand -hex 32`. Store only in deployment secret management or local `.env.local`; never commit them or expose them as `NEXT_PUBLIC_*`. One encrypts NRIC with AES-256-GCM; the other creates a keyed duplicate-detection hash. Loss or rotation requires a planned re-encryption/re-hash of existing identifiers; retain protected key backups. Patient directory responses do not decrypt NRICs; the detail endpoint requires `patients.identifiers.read`, records each successful reveal in `audit_events`, and returns no identifier if audit logging is unavailable. The service-role key must stay server-only. Registration requires an explicit operator attestation that patient consent was obtained.

Clinical document issue/revision and verification QR generation also require `DOCUMENT_QR_SIGNING_KEY`, a separate 32-byte server-only key (`openssl rand -hex 32`). The QR carries an opaque HMAC-derived token scoped to the document version; PostgreSQL stores only its SHA-256 digest. Rotation invalidates previously printed QR links unless tokens are reissued. The public verification endpoint returns only `valid` or `revoked`, and currently has no shared rate limiter.

Set `APP_BASE_URL` to the clinic application's canonical public HTTPS origin. Production QR URLs use this configured origin instead of request host headers.

## Data and access notes

- RLS first checks `auth.uid()` against `staff_members(auth_user_id, clinic_id, branch_id, active)`, then checks explicit branch+role+permission rows for operational tables. Branch membership alone does not grant module access. Staff management and permission edits are manager-gated. Any cross-branch administrative workflow must explicitly add the user to each branch.
- Public callers can invoke `verify_clinical_document(token)` through `/api/document-verification`, which returns only `valid` or `revoked` (unknown, expired, and revoked tokens all produce `revoked`). The server derives a version-scoped opaque token from the QR signing key and stores only its SHA-256 digest. The endpoint does not return names, diagnoses, dates, or other document data. There is no shared rate limiter yet.
- Clinical document versions, print logs, queue events, stock movements, package redemptions, delivery logs, and audit events reject update/delete. Ledger/history inserts are restricted to trusted server code; the authenticated browser role cannot insert synthetic history rows. Represent corrections with a new version/event or an explicit document revocation.
- Patient national identifiers should be encrypted by the application before writing `national_id_ciphertext`; the optional `national_id_hash` should be a keyed HMAC suitable for duplicate matching. Do not put secrets or plaintext NRIC values in logs or metadata.
- The system remains incomplete. Patient list/create, queue operations, and clinical document issue, immutable revisions, status-only QR verification, and print logs are database-backed. Appointments, rooms, encounters/prescriptions, inventory, packages, invoices/payments/receipts, notifications, commissions, and much of administration are not operational. Configure permission rows, server secrets, provider integrations, backups, retention, and access controls before storing real patient data. `NEXT_PUBLIC_CLINIC_DEMO_MODE=true` keeps the UI's supported demo workflows local; it does not disable server routes for direct authenticated API requests.
